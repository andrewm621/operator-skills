# maestro

Maestro is the standing command deck for cross-provider, cross-session orchestration — tasks, claims, worktrees, channels, and a derived board that live in the filesystem (not a chat session), so any terminal or provider (Claude Code, Codex, Cursor, Grok Build) can pick up a task where another left off, and post/read messages tied to it. Where `/orchestrate` decomposes and runs a goal inline in one session, `/maestro` is the durable substrate underneath it — and once a goal is a standing effort, `/orchestrate` seeds tasks onto this board instead of (or alongside) spawning inline.

Arguments: {the text you type after the command}

**Config:** `owner.handle` (default `$USER`) and `paths.projects` (default `~/Projects`) from `~/.config/operator-skills/config.yaml` — see `docs/config.md`. `maestro.mjs` reads both keys itself (zero-dependency reader); the environment variables `MAESTRO_HANDLE` and `MAESTRO_PROJECTS` override them. Missing file or key → default; never guess. Below, `<handle>` is `owner.handle` and `<projects>` is `paths.projects`.

**Current scope: `board` (default), `new`, `claim`, `heartbeat`, `sync`, `work`, `route` — all four providers (`claude`, `codex`, `cursor`, `grok`) are wired in `route` — plus the L2 comms verbs `say`, `read`, `ask`, `answer`, `inbox`, `handoff` — plus `mirror`, the GitHub-issue mirror — plus the lifecycle verbs `release`, `block`, `done` and `reap`, and `emit`/`status`/`who` (event-log verbs, available once the sibling `events.mjs` is installed).** `done` is a **reviewer or human action** — a worker that finishes its task sets `review` and stops; it never runs `done` on its own work.

All state lives under `<projects>/.maestro/` (global, derived — never hand-edited, includes `worktrees/`, `channels/fleet.md`, `inbox.jsonl`) and `<repo>/.maestro/` (per-repo, authoritative, includes `channels/`). Full schema in this repo's `docs/maestro-spec.md` (board/tasks) and `docs/maestro-comms-spec.md` (messaging). Every subcommand below is a thin wrapper over `node maestro.mjs <subcommand> ...`, which lives right next to this file. **Locate it before the first call** (first match wins; the directory this SKILL.md was loaded from comes first, then the standard install locations, then a repo checkout; `pwd -P` resolves symlinks to the real directory):

```bash
for d in "${MAESTRO_HOME:-}" "<directory this SKILL.md was loaded from>" ~/.claude/skills/maestro \
         ~/.claude/skills/operator/maestro ~/.agents/skills/maestro ~/.codex/skills/maestro \
         "${PROJECTS:-$HOME/Projects}/operator-skills/skills/maestro" ~/operator-skills/skills/maestro; do
  [ -n "$d" ] && [ -f "$d/maestro.mjs" ] && { MAESTRO_DIR="$(cd "$d" && pwd -P)"; break; }
done; echo "${MAESTRO_DIR:-NOT FOUND}"
```

If it prints `NOT FOUND`, stop and tell the user: `maestro.mjs` must sit next to this skill (it ships in the operator-skills repo's `skills/maestro/`); install the skills with the standard symlink or set `MAESTRO_HOME` to the folder containing it. Run every command below as `node "$MAESTRO_DIR/maestro.mjs" <subcommand> ...` (the table abbreviates this to `node maestro.mjs`).

## Steps

1. **Parse the subcommand** from `{the text you type after the command}` — the first token is the subcommand, everything after it is passed through verbatim (quoted title/text, `--flag value` pairs).

   | Input | Runs |
   |---|---|
   | (empty) or `board [--json]` | `node maestro.mjs board` |
   | `new "<title>" [--repo R] [--provider P] [--after T-x] [--priority N]` | `node maestro.mjs new "<title>" ...` |
   | `claim T-<id> [--repo R] [--owner O] [--steal] [--resume [--takeover]] [--force]` | `node maestro.mjs claim T-<id> ...` |
   | `heartbeat T-<id> [--repo R]` | `node maestro.mjs heartbeat T-<id> ...` |
   | `sync` | `node maestro.mjs sync` |
   | `work [T-<id>] [--resume [--takeover]] [--force]` | `node maestro.mjs work T-<id> ...`, then read + act on what it prints (step 6) |
   | `route T-<id> claude \| codex \| cursor \| grok` | `node maestro.mjs route T-<id> <provider> ...`, then act per step 7 |
   | `set T-<id> [--issue X] [--status S] [--client C] [--depends-on T-1,T-2] ...` | Internal helper — `node maestro.mjs set T-<id> ...` (used by step 7, not usually invoked directly) |
   | `say <T-id\|fleet> "text" [--repo R]` | `node maestro.mjs say ...`, then act per step 9 |
   | `read <T-id\|fleet> [--since ts] [--json] [--repo R]` | `node maestro.mjs read ...`, then act per step 9 |
   | `ask <T-id\|fleet> "question" [--to who] [--repo R]` | `node maestro.mjs ask ...`, then act per step 9 |
   | `answer <M-id> "text" [--repo R]` | `node maestro.mjs answer ...`, then act per step 9 |
   | `inbox [--for who] [--json]` | `node maestro.mjs inbox ...`, then act per step 9 |
   | `handoff <T-id\|fleet> --to who "text" [--repo R]` | `node maestro.mjs handoff ...`, then act per step 9 |
   | `mirror [--repo R] [--dry-run]` | `node maestro.mjs mirror ...`, then act per step 10 |
   | `release T-<id> [--repo R]` | `node maestro.mjs release T-<id> ...`, then act per step 11 |
   | `block T-<id> --by <@person\|external:x\|resource:x\|T-id> "reason" [--repo R]` | `node maestro.mjs block ...`, then act per step 11 |
   | `done T-<id> [--repo R] [--no-merge]` | `node maestro.mjs done ...` — reviewer/human only, act per step 11 |
   | `reap [--dry-run]` | `node maestro.mjs reap ...`, then act per step 11 |
   | `emit <type> [k=v ...]`, `status [--task X] [--json]`, `who <path\|T\|resource>` | `node maestro.mjs emit\|status\|who ...` — event-log verbs; if it prints `events module not installed`, report that and stop |

2. **`board` (default)** — Run `node maestro.mjs board` (it syncs first, then prints `board.md`). Don't just paste the raw markdown back — read it and present it like a status report: lead with what's actionable — the **⚑ NEEDS YOU** block first if it's non-empty (an open question is blocking someone), then the oldest open high-priority task, then any `STALE` claim, then the grouped table. `--json` emits the same rows the human render is built from (array of task objects, `needs_human` included) — use it when you need to reason about the board programmatically instead of re-parsing markdown.

3. **`new`** — Before running, sanity-check the title captures the true intent (same instinct as `/orchestrate` step 1 — the surface ask isn't always the real goal), and infer `--repo` from the current working directory if the user didn't name one and it's obvious. Run the command, then report the new `T-<id>` and where the task file landed.

4. **`claim`** — Run the command as given. If it fails with "not ready, waiting on: …", the task has an unfinished `depends_on` or a `blocked_by` — report what it's waiting on and stop; `--force` (logged to the task channel) is the human's call, not yours. `--resume` re-claims a task your own role-level actor (`<provider>@<host>`) already holds, e.g. after a restart — use it instead of `--steal` for your own work. If the claim is still *live* in a different session it refuses; `--takeover` overrides, but only when you know that other session is dead (it is logged like a steal). If it fails with "owned by ... live", report that plainly and stop — don't retry with `--steal` on your own initiative; a live claim means another session or provider is actively on it. If it instead fails because the claim is **stale**, that's the one case where suggesting `--steal` is appropriate: say who the stale owner was and how long ago the heartbeat lapsed, then confirm (or, if the user's instruction already implied "take it regardless," proceed straight to `--steal`).

5. **`heartbeat` / `sync`** — Run directly, report the one-line result. `sync` is a full rebuild of the global board *and* comms projections (`index.jsonl`'s `needs_human` counts, `inbox.jsonl`) from per-repo task/channel files — safe to run anytime; it never mutates task or channel files themselves.

6. **`work T-<id>`** — the load-bearing worker loop, and the one subcommand where "run it and report" isn't enough:
   1. Run `node maestro.mjs work T-<id> [--repo R]`. It claims the task, spins a sibling git worktree on branch `maestro/T-<id>-<slug>`, seeds `PROMPT.md` + `AGENTS.md` into it, seeds the todos file from the task's Acceptance boxes if empty, and flips status to `in-progress`. If it fails (not a git repo, branch/worktree already exists, or the claim is live elsewhere), it rolls the claim back to `open` before failing — report the error as-is, don't retry blind.
   2. **Read the printed `PROMPT.md`**, then the repo's own `CLAUDE.md` (or README), then the task's context pointers — in that order, before touching any code. A cold read of the brief without the repo's conventions is how you reinvent a pattern that already exists.
   3. Work the todos file (`<repo>/.maestro/todos/T-<id>.todos.md`) item by item — check boxes as you finish them, and run `node maestro.mjs heartbeat T-<id> --repo R` on each update so a `sync` elsewhere doesn't see this claim as stale mid-task.
   4. **If you get blocked or hit a decision you can't make**, don't stall silently — `node maestro.mjs ask T-<id> "…" --repo R` (add `--to <agent>` instead of the default `@<handle>` if it's a question for a specific teammate, not the human), then either keep working another todo item or stop and wait. Check `node maestro.mjs read T-<id> --repo R` for the answer before resuming that thread of work.
   5. When every Acceptance box is checked and the build/type-check passes, flip status with `node maestro.mjs set T-<id> --repo R --status review` and say so — don't leave it silently `in-progress` once the work is actually done. **Stop at `review`**: `done` (merge + teardown) is for a reviewer or the human, not the worker. If you are blocked on a person, a credential or another task, use `block` (step 11) rather than stalling.

7. **`route T-<id> <provider>`** — hand a task to another provider instead of working it yourself. All four providers seed the same worktree + `PROMPT.md` + `AGENTS.md`; only the printed launch string differs (spec §7):
   1. Run `node maestro.mjs route T-<id> <provider> --repo R`. If the launch string's binary (`cursor-agent` for `cursor`, `grok` for `grok`) isn't on PATH, the CLI still prints the launch string — it prepends a `note:` advisory instead of blocking. Relay that note plainly if it appears; don't strip it.
   2. **`claude`**: present the printed launch string — the human opens the terminal and runs it themselves (`/maestro work T-<id>` in the new session). v1 dispatch is human-in-the-loop by design (spec §7) — never spawn the other provider's process yourself.
   3. **`codex`**: after the CLI prints its two-step instructions, actually invoke `/handoff T-<id>` yourself to create the GitHub issue, then record the result with `node maestro.mjs set T-<id> --repo R --issue gh#<n>` so the task file and board reflect it. Only then present the final launch string — don't hand over a string that references an issue that doesn't exist yet.
   4. **`cursor`**: the printed string pipes `PROMPT.md` via stdin into `cursor-agent -p "Execute the attached task brief" --force --output-format json` (headless print mode; brief piped rather than passed as an arg to avoid CLI length limits). Note the binary is `cursor-agent`, **not** bare `agent` — on a machine with Grok Build also installed, plain `agent` on PATH can resolve to Grok's own CLI instead. Just present the string; don't "fix" the binary name back to `agent`.
   5. **`grok`**: the printed string pipes `PROMPT.md` via stdin into `grok -p "Execute the attached task brief" --cwd . --always-approve`. `--cwd .` points grok at the worktree already seeded for it — never suggest grok's own `-w`/`--worktree` flag, which would create a second, nested worktree.

8. **`set` / handoff-recording** — this is an internal helper (used in step 7.3 to record `--issue gh#<n>`, and available generally for `--status`/`--owner`/`--priority` field fixes). Don't reach for it as a first choice over `claim`/`work`/`route`/`answer`, which already do the right field updates as a side effect of the real action.

9. **The L2 comms verbs** — `say`/`ask`/`answer`/`read`/`inbox`/`handoff` post to and read from a task's channel (`<repo>/.maestro/channels/T-<id>.md`) or the cross-task `fleet` channel (`<projects>/.maestro/channels/fleet.md`). All four (besides `read`/`inbox`) are one-way appends — the only in-place edit in the whole system is `answer` flipping its ask's `#open`→`#resolved`.
   1. **`say`** — post a broadcast/status update to a thread. Use it for "here's what happened," not questions.
   2. **`ask`** — post a question tagged `#open`, prints the new `M-id`. Defaults to `--to @<handle>` (the human); pass `--to <agent>` for a teammate. This is how you seed step 6.4's "ask when blocked" behavior — don't paraphrase a blocking question into `say`, it needs to land in `inbox`.
   3. **`answer <M-id>`** — reply to a specific ask and resolve it in one shot. Works without `--repo` (it resolves the channel from the `M-id` itself) unless the same task number is ambiguous across two registered repos, in which case the CLI will tell you to add `--repo`. After answering, the asker sees it on their next `read`/heartbeat — there's no push, so if it's urgent, say so out loud too.
   4. **`inbox [--for who]`** — the "needs a human/agent" queue. Default is the human's (`<handle>`'s) open asks (this is what backs `board`'s ⚑ block); pass `--for <agent>` to check what's waiting on a specific teammate instead. `--json` for structured output.
   5. **`read <T-id|fleet> [--since ts]`** — print a thread, optionally only what's new since a timestamp (useful right after a heartbeat to check for an answer without re-reading the whole history). `--json` for structured output.
   6. **`handoff <T-id> --to <agent> "text"`** — like `say` but explicitly a context transfer to a named agent, not a broadcast. Use this over `say` when you're specifically handing work/context to a teammate, so it reads clearly in the thread as a handoff rather than a status ping.

10. **`mirror`** — the GitHub-issue mirror, and the **only** networked subcommand in the whole CLI; `sync`/`board` never shell out to `gh`. Opt-in per repo via a `mirror: github` key under that repo's entry in `registry.yaml` (absent = off, nothing happens). Run `node maestro.mjs mirror [--repo R] [--dry-run]` — no repo = every opted-in repo in the registry.
   1. **Status → GitHub state/labels:** `open`/`claimed`/`in-progress`/`review`/`blocked` stay an **open** issue labeled `maestro` + `maestro:<status>`; `done` **closes** the issue (label `maestro:done`). Labels are status-only — there's no assignee; owner lives in the body footer instead.
   2. **No `issue:` in frontmatter yet** — the CLI first tries to recover a pre-existing `label:maestro` issue whose body contains this task's hidden `<!-- maestro-task: <repo>/T-<id> -->` marker (adopts its number); only if nothing matches does it create a new issue. Either way it immediately writes `issue: gh#<n>` back onto the task file via the existing `set` setter — you don't need to run `set` yourself.
   3. **`issue:` already present** — it patches title/body/labels/state only on drift (never a no-op `gh issue edit`), diffed against a single batched `gh issue list --label maestro --state all` call per repo (not one call per task).
   4. **`--dry-run`** prints the exact `gh issue create`/`edit`/`close`/`reopen` commands it would run, with resolved labels/state and the body-file path, without executing anything — always start here on an unfamiliar repo.
   5. One task's `gh` failure is caught and reported inline; it never aborts the rest of the batch. If `gh` itself isn't installed, the whole run skips with a warning instead of failing.
   6. A task flipped to `done` (by `done` or `set`) only closes its mirrored issue on the *next* `mirror` run — that's expected, not a bug to chase.

11. **The lifecycle verbs** — `release`, `block`, `done`, `reap`:
    1. **`release T-<id>`** — drop the claim, task back to `open`, worktree kept. Use it to hand work back without finishing it (post a `handoff` or `say` first so the next claimer knows where you stopped).
    2. **`block T-<id> --by <blocker> "reason"`** — status `blocked`, `blocked_by` + `blocked_reason` written, claim kept. A blocker is `@person`, `external:<who>`, `resource:<name>` or another task id (comma-separate several). `--by @<handle>` also files an `ask` on the task channel so it reaches that person's `inbox` and the board's NEEDS YOU block. The task is not `ready` again until `blocked_by` is cleared (`set T-<id> --status in-progress` does it, or `set … --blocked-by none`).
    3. **`done T-<id> [--no-merge]`** — **reviewer or human only.** It refuses unless the status is `review`, every Acceptance box is checked, and the task channel has no open ask. Without `--no-merge` it merges the task branch into the repo's default branch, removes the worktree, deletes the branch, sets `done` and releases the claim. If the merge conflicts it aborts cleanly, marks the task `blocked` (`blocked_by: [conflict:<default-branch>]`) and exits non-zero — report the conflicting files and stop; don't resolve them on the reviewer's behalf unless asked. If the repo checkout is dirty or off its default branch it refuses and you fall back to `--no-merge` plus a manual merge. Never run `done` on a task you worked yourself.
    4. **`reap [--dry-run]`** — releases claims that have been silent for over 2× the TTL **and** whose worktree is clean; dirty or unpushed work is never touched and is listed under "⚑ needs you: abandoned work". Always start with `--dry-run` by hand; the scheduled job (`skills/maestro/launchd/`) runs the real thing every 5 minutes alongside `sync`. Surface the "needs you" block to the human verbatim.
    5. **Readiness** — `board` and `index.jsonl` show a `waiting on` column and `ready` flag derived from `depends_on` and `blocked_by`; `work`/`claim`/`route` won't take a task that isn't ready. When picking work, take a `ready` task. A `cycle` in `waiting on` is a data bug in `depends_on` — report it.

12. **Report** — Always surface the actual command output, or a faithful summary of it — never a paraphrase that hides an error. A non-zero exit is usually load-bearing here (e.g. "owned by X" is proof the atomic claim did its job, not a bug to smooth over).

## Notes
- **Ask when blocked, don't stall silently.** If you're working a task via `work` and hit a decision you can't make or a dependency you don't control, `ask` is the correct move — not guessing, and not going quiet. Check `read` for the answer before resuming that thread. This applies to every provider, not just Claude — the seeded `PROMPT.md`/`AGENTS.md` in each worktree should carry the same instinct forward.
- `work` and `route` spin real git worktrees as siblings of the repo (`<projects>/.maestro/worktrees/<repo>/T-<id>/`, never nested inside it) and seed the vendor-neutral `PROMPT.md`/`AGENTS.md` brief (spec §6). Use `done` (reviewer/human), `block` and `release` for merge-and-teardown, blocking and un-claiming — don't hand-roll them with `git worktree remove` or `set`.
- `/orchestrate` is the planning front door; once a goal is a standing, cross-session effort — or you want to hand pieces to another provider — persist the decomposition here via `maestro new "<title>" --repo R --provider <hint>` for each task, carrying the `provider_hint` you'd route to, then print the board.
- Owners are role-level ids, `<provider>@<short-host>` (e.g. `claude@macbook-air`), stable across restarts; the per-session part lives in the claim file's `session` field (`MAESTRO_SESSION`, else Claude Code's `CLAUDE_CODE_SESSION_ID`, else `CLAUDE_SESSION_ID`, else random). `MAESTRO_HOST` overrides the host part. **The provider part defaults to `claude`; Codex, Cursor and Grok sessions must `export MAESTRO_PROVIDER=codex` (or `cursor`/`grok`) before calling maestro**, otherwise they will claim as `claude@<host>` and be indistinguishable from Claude (`route` already puts it in the launch strings it prints). Older owners like `you@claude` still display.
- `<projects>/.maestro/policy.yaml` (hand-kept, optional; example in `docs/maestro-policy.example.yaml`) maps repos to clients; `sync` writes the result into each index row's `client` unless the task has its own `client:` field.
- The registry (`<projects>/.maestro/registry.yaml`) is hand-maintained — add a repo to it by appending a `- name` / `path` pair, and opt that repo into `mirror` by adding a `mirror: github` line under it (absent = mirror off for that repo). Everything else under `<projects>/.maestro/` (including `worktrees/`, `channels/fleet.md`, `inbox.jsonl`) is derived-or-authoritative-but-safe-to-regenerate-from-source — except don't delete a worktree by hand while it's in `git worktree list` (use `git worktree remove`), and never hand-edit `board.md`/`index.jsonl`/`inbox.jsonl` (all three are rebuilt wholesale by `sync`).
- `mirror` is the one place this CLI shells out to a network command (`gh`) — it is never invoked implicitly by `sync`/`board`/`work`/`route`, only when you (or the human) explicitly runs `maestro mirror`. Local `.maestro/tasks/*.md` frontmatter stays authoritative either way; the GitHub issue is a read-mostly mirror of it, not the other direction.
- Per-repo `.maestro/tasks/*.md`, `.maestro/todos/*.md`, and `.maestro/channels/*.md` are the real, editable/appendable source of truth. `board.md`, `index.jsonl`, and `inbox.jsonl` are derived projections of them — a manual edit to any of the three is silently discarded on the next `sync`.
- The `/handoff` **skill** referenced in step 7.3 (GitHub-issue creation for Codex; it ships in this repo as `skills/handoff`) is a different thing from the `handoff` **verb** in step 9.6 (a comms message) — same word, two layers. If the skill isn't installed or `gh` isn't authenticated, say so rather than faking an issue number.
- `cursor`/`grok` launch strings are printed, never run automatically — v1 dispatch is entirely human-in-the-loop (spec §7). Some of their flags (Grok's non-interactive/approval flag in particular) are best-effort corrections from a real `--help` read, not a verified live run — flag that if the human hits a flag error running one themselves, and update `maestro.mjs`'s `ADAPTERS` table rather than guessing again.
- Text that starts with `-` (a `say`/`ask`/`answer`/`handoff` message, a `block` reason, a `new` title) must come after a bare `--`, with any flags before it: `maestro block T-3 --by @andrew -- "-5% churn blocks this"`. Without `--` such text is rejected rather than misread as a flag.
- Comms is pull-based, no daemon (comms spec §5) — an offline agent just reads the thread when it resumes. Don't treat a `say`/`ask` as guaranteed to be seen promptly; if something is truly time-critical, tell the human directly in addition to posting it.
